## 总体评价

工程质量**明显高于同类个人项目**。这些方面做得扎实，**无需改动**：

- TypeScript strict 零 `any`、零 `@ts-ignore`；78 个 API 端点 100% 声明 `prerender = false`
- 双 schema（SQLite/PG）字段级一致，布尔/时间戳用 customType 统一编码（有事故注释守护）
- 主备双写 + 断路器设计完善，纯逻辑可单测
- MDX 管线有 6 层源码预处理 + LRU 缓存，每个函数都有事故根因注释
- 无障碍基础良好：Tabs 有 `role=tablist` + 键盘导航、DeerDots 完整 `prefers-reduced-motion`、`safeNextPath` 防开放重定向
- 254 个单测全绿

**主要债务**集中在三类：**单文件膨胀**、**样板代码未抽象**、**详情页全表查询**。

## P0 严重（建议优先修）

### P0-1 详情页全表查询，阅读延迟随文章数线性增长
**位置**：`src/pages/blog/[slug].astro:46-49`、`src/pages/doc/[id].astro:20,51`

```ts
// blog/[slug].astro:46 —— 加载全表元信息，只为算上一篇/下一篇
const all = await listArticleMeta();
const idx = all.findIndex((a) => a.id === article.id);
```

**原因**：为拿相邻两篇文章，把全表拉进内存再 `findIndex`。文档页更重 —— `doc/[id].astro:51` 调 `listDocTree()`，该方法**无 where 全表扫 4 张表**（categories/bundles/articles/nodes），而页面只用了一个分类名做面包屑。

**影响**：文章/文档数增长后，**每次阅读都付 O(N)**。500 篇文章时每次详情页多扫 500 行 + 500 次 `parseTags`。这是最直接的体验损耗。

**改进**：
```ts
// 两条 SQL 替代全表（走 updatedAt 索引）
const [next] = await db.select(META_COLUMNS).from(articles)
  .where(gt(articles.updatedAt, article.updatedAt))
  .orderBy(asc(articles.updatedAt)).limit(1);
const [prev] = await db.select(META_COLUMNS).from(articles)
  .where(lt(articles.updatedAt, article.updatedAt))
  .orderBy(desc(articles.updatedAt)).limit(1);
```
文档页面包屑：`getBundle()` 已带回 `categoryId`，只需单条 `select name where id=?`。

### P0-2 搜索全表取正文 + 逐篇正则扫描，CPU 与内存双爆
**位置**：`src/pages/api/search.ts:36` → `src/lib/search.ts:48-61`

```ts
const all = await listArticles();          // 取全表，含每篇 content
// matchArticle 内：对每篇调 stripMarkdown(a.content)（12 次正则替换）
```

**原因**：无 FTS、无 limit 前置、无元信息粗筛。每次搜索对所有文章正文做全量正则剥离 + `toLowerCase`。

**影响**：已实证 `listArticles` 取全量列。500 篇 × 30KB 正文 ≈ **15MB 字符串 + 500 次正则扫描**，且搜索框每次输入都可能触发。

**改进**：先按 `META_COLUMNS`（title/summary/tags）粗筛，仅对命中项做正文剥离；或加 `content_text` 冗余列（保存时算好）配 SQL `LIKE`。

### P0-3 点赞计数「先读后写」竞态
**位置**：`src/lib/comments.ts:276-302`、`src/lib/likes.ts`

**原因**：先 `SELECT likeCount` 再 `UPDATE likeCount = current ± 1`，read-modify-write **非原子**。且 `likes` 表**未声明唯一约束**（`likes.ts:122` 注释自称「唯一约束兜底」，但 schema 里没有）。

**影响**：并发点赞丢更新；评论点赞可能出现「like 行已删、count 未减」的永久偏差。

**改进**：
```ts
// SQL 自增替代读改写
await db.update(comments).set({ likeCount: sql`${comments.likeCount} + 1` })
```
并给 `likes(targetType,targetId,userType,userIdent)` 补唯一索引。

### P0-4 级联删除无事务，双库易留孤儿数据
**位置**：`src/lib/docs.ts:102-105`、`147-151`

**原因**：`deleteDocCategory` 先循环 `deleteDocBundle`（内含 3 次独立 `db.delete`）再删分类，**全程无事务**。而 `db.delete` 走双写 Proxy，失败仅 `console.error` 不阻断。

**影响**：主库成功 / 备库失败 → 数据分叉；中途失败 → 分类残留而文档已删。

**改进**：用 `db.transaction()` 包裹级联；或改 `onDelete: 'cascade'` 外键让 DB 原子处理。

**位置**：`src/lib/images.ts:44,88`、`src/lib/object-storage.ts:75`（已实证）

## P2 次要

### 动画与渲染

**P2-1 全站 `mousemove` 粒子持续创建 DOM** — `BaseLayout.astro:441-448`
40ms 节流后每次仍创建 3 个 `<span>` + `appendChild`，长页面持续移动鼠标 ≈ **每秒 75 个节点**创建/销毁。建议改用 CSS 变量 + 单 canvas 粒子层，或提高节流到 80-120ms 并限同屏粒子总数。

**P2-2 DeerDots 每帧 4.2 万次迭代 + 定时器未清理** — `src/components/DeerDots.astro:191-268,299-306`
1080p 屏 SPACING=10 → 约 21000 个点，`draw()` 内两个完整遍历 = 42000 次迭代/帧，且鼠标半径内每点调 2 次 `Math.random()`。更关键的是 `:299` 的空闲心跳 `setTimeout` **未存句柄，`stop()` 无法取消**；`pointermove` 里每次 `getBoundingClientRect()` 强制同步布局。建议：存心跳句柄并在 `stop()` 清理、缓存 rect、降低网格密度。

**P2-3 日历 tooltip 触发 fetch 且无取消** — `src/pages/calendar/index.astro:350-380`
`mouseover` → 2s 延迟 → `await fetch('/api/diary')`，鼠标快速划过 6×7 格子会**请求风暴**，且无 `AbortController`，`mouseout` 无法取消在途请求。

**P2-4 动画触发布局属性** — `src/styles/global.css:253`（`scroll-progress` 动画 `width`）
建议改 `transform: scaleX()` + `transform-origin: left`，走合成器。

**P2-5 `clip-path` 大面积动画** — `src/styles/global.css:1076-1096`（`hero-break`）
`clip-path: inset()` 逐帧变会**重新光栅化整个 hero 大图**。建议改 `mask-image` + `transform: translateX`。

**P2-6 常驻 `will-change` 吃显存** — `src/styles/global.css:806`（`.hero-char`）
Hero 每个字一个 span + 常驻 `will-change: opacity`，一首诗 20+ 个合成层。建议移除（动画量小，收益 < 成本）。

**P2-7 全屏 `backdrop-filter`** — `global.css:374`（`.nav-loader` 全屏 blur）、`BaseLayout.astro:170`（header 常驻）
建议 `.nav-loader` 改纯色半透明，header 加 `@supports` 降级。

**P2-8 长列表缺 `content-visibility`** — `Timeline.astro:31-46`、`ActivityHeatmap.astro:95-109`（371 个 `.heat-cell`）、`moments/index.astro`
建议加 `content-visibility: auto; contain-intrinsic-size`。

**P2-9 瀑布流 resize 不重排 + 强制同步布局** — `src/pages/gallery/index.astro:223-276`
`columnCount()` 只在首次执行，窗口拉伸后列数不变（**功能 bug**）；`appendToShortestColumn` 每次遍历所有列读 `scrollHeight`（30 张图 = 30 次强制布局）。

**P2-10 定时器未清理** — `src/scripts/copy-button.ts:24-29`（快速连点叠加）、`RightToolbar.astro:80-95`（2s 轮询无取消）

### 数据与方言

**P2-11 `like` 在 PG 上大小写敏感** — `docs.ts:226,246,257`、`photos.ts:93,186`、`moments.ts:129,133`
SQLite `LIKE` 对 ASCII 不敏感，**PG `LIKE` 敏感** —— 注释声称的「大小写不敏感」在生产不成立。建议统一改 `ilike`。

**P2-12 `count()` 未转 Number** — `articles.ts:99-100`、`photos.ts:187`
PG 的 `count()` 返回 **bigint 字符串**，`rows[0]?.n ?? 0` 未转换，前端比较/加法会出错。建议 `Number(rows[0]?.n ?? 0)`。

**P2-13 批量操作逐条往返** — `photos.ts:253-271`（N 次 SELECT + N 次 UPDATE，双写下 2N 次写）、`docs.ts:389-391`（循环 DELETE）
建议 `inArray()` 批量处理。

**P2-14 `uniqueSlug` 循环内查库** — `articles.ts:162-171`
最坏 98 次 DB round-trip。建议一次 `inArray` 取候选集。

### 结构与依赖

**P2-22 死依赖** — `package.json`（已实证 0 引用）
`giscus`（评论已换自建）、`codemirror`（只用 `@codemirror/*` 分包）、`mdast-util-mdx-jsx` 可直接删。

**P2-23 双渲染管线并存** — `src/lib/mdx.ts`（`@mdx-js/mdx`）vs `src/components/ai/AiChatFloat.tsx:23`（`marked`）
两套 Markdown 语义（callout/公式）**必然漂移**。建议 AI 回答复用 `/api/doc/preview`，移除 `marked`。

**P2-24 失效逻辑写错但被 hash 机制救回** — `src/lib/mdx.ts:68-70`（已实证）
```ts
export function invalidateRenderCache(source: string) {
  RENDER_CACHE.delete(djb2(source));   // ← 写缓存用的是 djb2(normalized)
}
```
`normalized` 是 6 个预处理函数的输出，**与原始 source 永远不等** → 该函数是彻底的 no-op。**实际影响有限**（改正文后新 hash ≠ 旧 hash，自然不命中），但改过的旧版本占着 100 条缓存槽位，挤压有效缓存。建议抽 `normalizeSource()` 单一函数，失效与写入共用。

**P2-25 djb2 哈希碰撞（理论风险）** — `src/lib/mdx.ts:42-46`（已实测复现）
实测 `" A"` 与 `"! "` 碰撞。32 位哈希 + 长度后缀，**两字符即可撞**。但真实文档为长文本，100 条缓存下碰撞概率约 2.3e-6，**实际罕见**。若求稳可改 `createHash('sha1')` 取前 16 字节。

**P2-26 文档与代码矛盾** — `docs/DESIGN.md:32` 仍写「+ Giscus」，`docs/DEPLOY.md:32` 仍教部署 giscus.app，而实际评论系统是自建/Twikoo。会误导新读者。

**P2-27 未鉴权端点的授权面靠约定守护** — `src/middleware.ts:20-75`
`/api/admin-auth/*`（授权账号增删改）**不匹配任何前缀分支**，完全绕过 middleware，唯一边界是端点内层 `isTopAdmin()`。经核对**当前实现正确**，但新增端点若忘记内层校验即裸奔。建议在 `requiredApiPermission` 显式声明 `startsWith('/api/admin-auth/')`。

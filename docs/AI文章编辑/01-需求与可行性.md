# AI 文章编辑：需求与可行性

日期：2026-10-08。状态：规划完成，尚未实现。

## 1. 目标

把当前「小卿」升级为能够读取站内内容、调用用户技能、修改当前文章的编辑助手。站主可以在博客内完成润色、整理笔记和调整 Markdown 排版，减少在博客与外部 Agent 之间复制粘贴的步骤。

采用 Pi 接入模型；保留站点现有的服务商、API Key 和模型设置。文章与文档继续使用现有布局、可视化编辑器和完整 Markdown 扩展渲染。

### 1.1 已确认的决策

| 项目 | 决策 |
| --- | --- |
| 选区入口 | 编辑模式下选中文字，右键出现「使用 AI 编辑」 |
| 整篇入口 | 在当前文章编辑模式下打开右侧 AI 聊天框，自动绑定当前文章 |
| 读取范围 | 当前文章，以及按需搜索、读取站内其他文章和文档 |
| 修改范围 | 第一版只修改当前打开的文章；其他文章作为只读参考 |
| 修改应用 | 明确要求修改后，生成完成、检查通过且原文未变化时自动替换并保存 |
| 交互 | 可继续聊天、停止生成、查看改动、撤销本次修改 |
| 技能机制 | 真正加载 `SKILL.md`；不把两个技能固化成代码内的提示词 |
| 权限 | 第一版编辑助手仅站主可用，普通聊天继续保留原有访问策略 |
| 首批平台 | 现有网页编辑器与 Electron 桌面版；原生 Android 编辑入口另行适配 |

## 2. 当前项目情况

### 2.1 AI 为什么目前不能编辑

当前 `/api/ai/chat` 转发普通对话消息，没有注册读取文章、加载技能、产生文章修改的工具。`AiChatFloat.tsx` 只发送对话历史和有限选区文字，没有与编辑器建立当前文章上下文。

项目已经具有可复用的基础：

- `MarkdownEditor.tsx`：CodeMirror 可视化编辑、历史记录及嵌套编辑器。
- `DocInlineEditor.tsx`：文档与首页文章共用就地编辑，正文变更自动保存。
- `cm-context-menu.ts`：已有自绘 Markdown 右键菜单。
- `cm-callouts.ts`、`cm-columns.ts`、`cm-table.ts`：Callout、分栏和表格就地编辑。
- `ai-config.ts`：数据库保存服务商、模型、密钥和生成参数。
- `renderMdx()`：项目权威 Markdown 扩展渲染管线。

因此，主要工作是打通编辑器、Agent 工具、技能库和版本校验，不需要替换整个文章系统。

### 2.2 当前配置的实际限制

本次只读检查桌面设置：已启用 AI，模型名称为 `deepseek-v4-flash`，经配置的 OpenAI 兼容中转地址调用，回答上限为 1,024 tokens。

1,024 tokens 应用于聊天，但不能直接作为整篇文章整理的输出预算。新增独立编辑预算，防止截断的正文覆盖文章。

尚未向当前模型发起真实请求。本次没有验证该中转接口的工具调用、上下文上限和更长输出能力；不能仅凭模型名称认定它支持这些能力。

## 3. 用户场景

### 3.1 选中文字进行编辑

1. 在首页文章或文档文章中进入编辑模式。
2. 选中文字，右键选择「使用 AI 编辑」。
3. 浮层显示文章名称、选区范围和选中文字，并提供聊天输入。
4. 输入「这段表达更清楚一点」「改成列表」「按我的笔记格式整理」等要求。
5. AI 根据选区、周边上下文及需要加载的技能生成修改。
6. 成功后只替换选区，保留其他正文；显示「已替换并保存」和撤销入口。
7. 可以继续针对新内容提出修改，或撤销上一轮。

没有选区时不显示该入口；现有 Markdown 操作菜单继续工作。阅读状态的「问问小卿」保持问答行为。

### 3.2 在右侧 AI 聊天中修改整篇文章

1. 进入当前文章的编辑模式，打开右侧 AI 聊天框。
2. 聊天框标明「当前文章：标题」，读取编辑器最新源码，包含尚未保存的输入。
3. 用户可以提问，也可以明确提出修改要求。
4. 「帮我解释第二节」只回答；「整理全文」「把第二节改为对照表」产生编辑操作。
5. 修改完成后在当前页面更新正文、目录和保存状态，不跳转编辑页面。
6. 切换文章后重新绑定目标，并清理旧文章的执行上下文，避免把修改写到另一篇文章。

### 3.3 自动调用两个技能整理笔记

例如：输入「把这篇笔记整理成我喜欢的格式」。

执行路径：发现技能 → 加载 `note-normalizer/SKILL.md` → 识别笔记类型 → 按该技能的路由规则加载 `my-blog-structured-notes/SKILL.md` → 生成 Markdown → 检查完整性和项目语法 → 自动更新当前文章。

模型可以自行选择技能；用户也能通过技能选择器或 `/skill:技能名` 显式指定。明确指定后必须加载对应文件，不能只凭技能名称猜测规范。

### 3.4 查阅其他文章

用户可要求「参考站内那篇文章来完善这里」。AI 搜索得到标题、摘要、ID 和站内链接，按需读取命中的正文片段。对话中显示所查阅的文章，其他文章不被改写。

读取包括站主有权访问的未发布和受保护内容；不会把整个数据库一次性发送给模型。不读取数据库连接串、API Key、源代码或电脑任意文件。

## 4. 技能维护体验

在「设置 → AI 助手 → 技能」管理首批两个技能：

- 查看和编辑完整 `SKILL.md`，保留 YAML 元信息、步骤、模板和示例。
- 导入文件、导出文件、启用或停用。
- 查看版本、修改时间、恢复历史版本。
- 技能有关联参考文件时，一并管理其 `references/`、`assets/` 文本资源。
- 保存后新任务使用新版本，无需重新构建桌面版。
- 已开始的任务固定使用开始时的技能版本，避免任务中途规则改变。

桌面端提供「本机技能目录」挂载模式，可以直接读取你原有的两个技能文件；修改原 `SKILL.md` 后新任务立即读取更新。挂载模式在站内显示为只读来源，避免两套编辑器同时改源文件；要在设置中编辑，可复制导入站内管理模式。

网页端使用站内管理模式，完整技能文件保存为可导入导出的技能包。每个技能只启用一个来源；不在本机原文件和站内副本之间隐式双向同步。桌面挂载路径只存在本机配置，不同步到云端。

## 5. 自动覆盖、保存和恢复

- 修改必须源于当前用户的编辑请求，闲聊和解释不自动改文章。
- 成功生成完整修改后才应用；不把流式半成品逐字写入文章。
- 空输出、长度截断、取消、模型错误、工具失败或渲染失败都保留原文。
- 生成期间可以继续手动编辑。若原文版本变化，则保留 AI 候选与当前内容，提示重新生成，不直接覆盖。
- 正常结果自动应用，不要求用户再点一次确认；改动对比是查看入口。
- 每轮 AI 修改独立进入撤销历史；提供「撤销本次修改」，撤销后也保存。
- 服务端保留修改前后快照，支持页面重开后的恢复；恢复同样校验当前版本。
- 不自动更改标题、分类、标签、访问保护和发布状态。已发布文章的正文保存会影响其正式内容，行为与当前正文编辑一致。

## 6. 可行性结论与范围

| 能力 | 评估 | 关键工作 |
| --- | --- | --- |
| 读取最新编辑内容 | 可行 | 编辑器上下文桥接，不能只读取数据库旧稿 |
| 选区 AI 替换 | 可行 | 持久的选区快照、嵌套容器位置映射 |
| 整篇整理并保存 | 可行 | 独立输出预算、分块、版本校验和恢复 |
| 真实技能加载与更新 | 可行 | 技能注册、按需读取、原文件版本管理 |
| 站内文章检索 | 可行 | 有权限的数据适配器、查询和读取预算 |
| Pi 接入现有服务商 | 方案可行，兼容性待验证 | 自定义 Provider，真实工具调用检查 |
| 任意电脑文件修改 | 不属于本次范围 | 本次写入文章数据库与编辑器 |

性能压力主要来自长文章的模型输入、完整技能文件和 Markdown 渲染。通过按需检索、按需加载技能、完整容器分块、每次候选只渲染一次和任务上限控制处理量。尚未进行性能基准测试，不承诺固定响应时间。

## 7. 首版验收场景

- 普通段落选区润色，不改变选区外内容。
- Callout、分栏子编辑器及表格单元格内选区可正确替换，容器结构保留。
- 右侧 AI 使用最新编辑内容，支持解释与整篇修改。
- 两个技能确实被加载，路由关系和显式指定都有效。
- 修改技能文件后，新任务的输出使用新规则；旧任务仍使用旧版本。
- 引用其他文章时来源可点击，仅当前文章被修改。
- 长文分块不漏内容，未闭合的公式、代码围栏和容器不会写入。
- 取消、断流、截断、冲突和失败均不损坏原文；撤销和历史恢复可用。
- 非站主不能调用编辑、技能管理和恢复接口；所有私密响应禁用公共缓存。

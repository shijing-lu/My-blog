# AI 文章编辑：使用与实现记录

## 一、使用方式

### 1. 先配置模型

在“设置 → AI 助手”中继续使用现有服务商地址、API Key 和模型名称。文章 Agent 与普通聊天共用这一配置，通过 Pi 的 OpenAI 兼容 Provider 调用；不从电脑环境变量取另一把密钥，也不会把代理模型名称替换成 Pi 内置模型名称。

“测试连接”与“测试工具调用”分别检查普通请求和工具调用。两项检查均由用户点击时才请求服务商。模型必须支持工具调用才能进行文章编辑；普通聊天可继续使用只支持文本回答的模型。

文章编辑具有独立的输出与上下文额度，初始值分别为 8192 和 131072 tokens。这是可调整的请求预算，不代表服务商已验证支持这些额度。请以服务商实际限制配置；调用失败、截断、超预算或流中断时不写入正文。

### 2. 编辑选中文字

在文档或首页文章的就地编辑器、文章写作工作区中选中文字，右键选择“使用 AI 编辑”。普通文本、Callout、分栏、选项卡、折叠内容和表格单元格共用同一个对话框。

对话框打开时冻结选区，失焦不会改变修改位置。选择整理技能并输入要求，例如“保留全部事实，使用笔记整理技能优化这段内容”。生成完成后自动替换、保存；不会把正在生成的半段文字逐字写入编辑器。

选区任务只返回所选文字的候选替换。容器的引用前缀、分栏围栏、折叠缩进及表格转义由编辑器适配器合成，完整正文通过服务端校验后才能保存。

### 3. 编辑整篇文章

进入文章编辑模式后点击右侧 AI 聊天按钮，即打开右侧文章助手浮窗；再次点击可收起。可以在生成期间继续编辑正文。它读取编辑器的最新内容：先冲刷表格等延迟输入及保存队列，再建立本轮版本基线。

普通问题只产生回答。明确要求修改、优化或整理时，AI 暂存完整候选或精确片段补丁，完成后统一保存。需要补充信息时，助手会提出问题，本轮不保存；用户补充后重新读取最新正文。

AI 可搜索、读取站内其他文章和文档，来源链接显示在对话框中。其他资料始终只读。第一版不处理加密文章，不提供任意磁盘读写、命令行或 SQL 工具。

长文章先判断本轮是提问还是全文整理。全文整理按完整 Markdown 容器分段，显示片段进度，每段使用同一份固定技能快照。处理完所有片段后才统一保存。最多 32 段，每段最多 8 次模型调用和 24 次工具调用；单个容器无法完整放入预算时明确报错，请在容器内选区处理或提高额度。选区任务在全文过长时提供所选内容与完整标题索引，并明确标注上下文范围。

### 4. 撤销与历史

保存完成后可点“撤销本次修改”，也可使用编辑器的一步撤销。正文修改在根编辑器中属于一个独立历史事务，嵌套编辑器不会单独写入服务器。

“修改历史”读取当前文章最近 20 个 AI 修改记录。可查看完整的修改前快照；当当前正文仍等于该次 AI 结果时，可以撤销并保存。若已有新修改，不强行覆盖，快照仍可复制出来处理。

## 二、技能维护

### 1. 保留真实技能文件

随项目保存两个原始 SKILL.md 的完整副本，用于首次初始化站点技能。没有将文件规则改写成固定系统提示词，也没有执行技能中的命令行示例。

技能加载流程为：目录元信息 → `read_skill` 读取完整文件 → 按路由读取其他技能及登记参考 → 完成整理。笔记任务先读取 `note-normalizer`，按其指引加载 `my-blog-structured-notes`。用户显式指定的技能必须读取后才允许写入。

### 2. 桌面端原文件挂载

桌面端首次初始化时，若当前账号 `.agents/skills` 下存在这两个原目录，会登记为本机技能来源。后续每个新任务重新读取原文件，不需要重新构建。

可在 AI 设置中选择文件夹、挂载其他目录或切换为站点版本。原文件只读，设置显示挂载路径和读取结果；路径失效时报错，不使用旧副本替代。本机路径保存在排除同步的 `ai_skill_mounts` 设置中。

相对资源只读取挂载目录内的 `.md`、`.txt`、`.json`，跳过符号链接、隐藏目录及 node_modules；目录层级和大小受限。任务第一次加载技能时固定源码和资源快照，中途修改原文件不影响本轮。

### 3. 站点版本

网页端使用数据库中的完整技能版本。AI 设置支持原文编辑、导入 SKILL.md、导出、查看历史版本、登记相对参考文件。保存后新任务读取新版本。

实现使用 `ai_skill_versions` 的不可变版本图，直接由父版本关系推导有效版本，替代规划中的独立 `ai_skills` 可变头表。同步按并集合并版本；并发保存产生分支时保留全部版本，AI 明确报错，需选择并整理后保存为合并版本。避免 LWW 自动丢弃另一端的技能修改。

项目 `docs/Markdown-语法手册.md` 为显式登记的参考资源，随构建嵌入；技能中的项目路径及 `.diag` 命令以参考读取和 Markdown 校验工具适配，不执行本机脚本。

## 三、服务端与数据保护

| 接口 | 功能 |
| --- | --- |
| `GET /api/ai/skills` | 技能目录、版本、挂载状态及原文 |
| `PUT /api/ai/skills` | 保存新版本、合并版本或切换来源 |
| `POST /api/ai/edit` | 流式运行文章 Agent，返回候选和修改记录 ID |
| `PATCH /api/ai/edit` | 校验、条件提交候选，支持同一 ID 幂等重试 |
| `PUT /api/ai/edit` | 条件撤销一轮已保存修改 |
| `GET /api/ai/edit` | 按当前文章查询历史；按记录 ID 读取快照 |

所有新接口在中间件和 handler 两层限制为站主，响应 `private, no-store`。客户端身份检查仅控制入口显示，不能代替服务端鉴权。

`ai_edit_runs` 保存原文、候选、基线时间、状态、技能快照和检索来源，仅留在当前站点，不参与跨端内容同步。SQLite 和 PostgreSQL 均登记 schema，首次调用时执行幂等 DDL，部署 SQL 同步补齐。

候选先编译、检查 AST，拒绝可执行 MDX、ESM、事件属性、不安全链接和未登记组件，然后使用完整 `renderMdx` 渲染验证。普通 Markdown 代码块里的示例代码不会当作脚本执行。安全限制针对执行能力；现有 Callout、分栏、表格、公式、折叠等扩展沿用项目管线。

提交前客户端核对文章、编辑会话和根正文；提交期间暂时锁定输入。服务端在同一事务中校验原正文及版本，保存正文和快照，保留标题、分类、发布状态。提交确认丢失可使用同一修改 ID 重试。

既有自动保存增加正文 SHA-256 条件写入，与标题更新分开判定；延迟请求不能覆盖不匹配的新正文。写作工作区保存改为串行合并队列，并跳过已经成功保存的相同请求，避免重复刷新文章版本引发 AI 提交冲突。AI 提交后清空该请求缓存并返回新正文版本，编辑器更新保存基线；后续手动输入及撤销继续正常保存。发生冲突时保留当前稿和候选，不静默覆盖。

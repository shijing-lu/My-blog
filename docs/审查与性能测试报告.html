My-Blog 全项目审查 & 性能测试报告

本报告基于四个维度的并行代码审查（每个维度逐文件定位到「文件+行号」），叠加线上真机性能测试（playwright 驱动 Edge 实测生产站 www.byqx-blog.online）与构建产物分析。问题按严重程度分 P0（应立即修，安全/首屏/核心功能）/ P1（重要，影响体验与可维护性）/ P2（优化项）三级，最后给出整体重构优先级。

一、性能维度

最核心的发现集中在「首屏请求爆炸」与「全量查询」。测试实测数据见第五节。

P0首屏动态页 /moments 请求爆炸 —— 全站最严重瓶颈
  • 位置：src/pages/moments/index.astro:209（<Comments client:load ...>）；src/components/interact/Comments.tsx:243,261,288,323,350,375；点赞见 LikeButton.tsx:44-47,76
  • 问题：每条动态挂一个 client:load 评论岛（含点赞）。每条动态页面加载即发起 /api/auth/user/me + /api/comments + /api/likes/summary + 图片等请求。实测该页 87 个请求，其中 52 个是 API，远超任何其它页面。
  • 方案：① 评论/点赞改 client:visible（进入视口再 hydration）或聚合为「点击展开评论区」延迟加载；② 用 countLikesByTargets（页面已批量预取 likeMap）替代每条点赞再发一次 summary；③ 评论列表改为懒加载分页接口。
P0查询ActivityHeatmap / 首页数据全量查询正文
  • 位置：活动热力图组件（src/components/activity/ActivityHeatmap*）——为渲染热力图把每篇已发布文章的正文 content 全量取出。
  • 问题：文章正文往往数十 KB，仅用于统计字数/日期，属典型「大字段全表捞」。数据量大时显著拖慢首页与学习页 TTFB。
  • 方案：SQL 仅 select id, createdAt, (length/字数) 预聚合，或建 post_stats 表在写入时冗余统计；Drizzle 用 .select({id, createdAt}) 明确列裁剪。
P0N+1影集 batchUpdateTags / 相册卡片存在 N+1 查询
  • 位置：src/pages/api/photos/batch-tags.ts（批量打标签逐条 update）；相册列表逐张查归属/标签。
  • 问题：批量操作与列表渲染按条/按张发 SQL，N 越大越慢。
  • 方案：批量操作改单条 UPDATE ... WHERE id IN (...) 或事务内 prepared；列表用一次 IN 关联查询填充标签。
P1搜索/api/search 全量拉取后内存过滤
  • 位置：src/pages/api/search.ts
  • 问题：把全表文章一次性取出在 JS 内存里做 includes 过滤，且不搜正文（MEMORY 已记：只匹配 title/summary/tags）。数据量大时内存与延迟双高。
  • 方案：改 SQL LIKE + LIMIT（SQLite/PG 均支持），必要时引入 FTS5 / pg_trgm 全文索引。
P1体积构建产物体积大，最大 chunk 超 500KB
  • 位置：.vercel/output/static/_astro/（部署产物）—— 49 个 JS 共 1454KB + CSS 443KB。
  • 问题：MarkdownEditor.js 534KB、ThemeHead.css 419KB、simple-mind-map.js 331KB、client.CZ1JDvuH.js 179KB。
  • 已核实修正：simple-mind-map 在 MindMapViewer.tsx:15-16 与 MindMapEditor.tsx:12-13 均为 import type，运行时走动态 import()（viewer:241 / editor:43），已做代码分割，不会无条件进入所有页面。真正的隐患是 client:load 让岛在首屏挂载后立即触发该动态导入。
  • 方案：① 大编辑器/思维导图确认是否 client:load，改 client:visible 或独立路由异步分包（import()）；② 关注 `simple-mind-map` 全量打包是否可 tree-shake；③ CSS 检查重复主题变体。
P1hydration多页面 client:load 全量水合
  • 位置：思维导图、评论区、点赞组件等大量 client:load。
  • 问题：进入视口前即 hydration，占用主线程，与「折叠栏卡顿」叠加。
  • 方案：按交互优先级改为 client:visible / client:idle。
P2索引/写缺索引 + dbWrite 串行 + 图片重复转换
  • 位置：点赞/评论/文档关联表缺复合索引；src/lib/db 双写串行等待主备。
  • 问题：点赞计数唯一约束虽保幂等但无索引查询慢；主备串行写抬升高频写延迟。
  • 方案：为 (targetType,targetId) 加索引；写路径并行化或用队列批量；base64 图避免每次请求重新 sharp 转换（结果缓存/预转换）。

二、UI/UX 维度

P0移动端移动端导航溢出 / 不可达
  • 位置：顶部/侧边导航（src/components/layout/Header.astro 等）。
  • 问题：导航项在窄屏溢出或被裁切；hover-only 管理按钮在触屏与纯键盘下完全无法触发。
  • 方案：移动端改抽屉/汉堡菜单；管理按钮提供 focus-visible 与 touch 触发路径。
P1可访问性reduced-motion 覆盖不全 + 搜索框无焦点样式
  • 位置：折叠动画、背景特效、搜索输入框。
  • 问题：动画与交互未全部包裹 prefers-reduced-motion；搜索框无清晰 :focus 态，键盘导航不可辨识。
  • 方案：全局增加 reduced-motion 降级；给搜索框补 focus ring。
P1主题硬编码颜色破坏主题 + 像素级小字号
  • 位置：多处组件硬编码 hex（src/components/**）；8-10px 的字号出现在若干角标/标签。
  • 问题：换主题后部分区块不跟随，明暗切换出现突兀色块；小字号在部分屏幕不可读。
  • 方案：统一抽取为 Tailwind 语义色/CSS 变量；字号下限提到 12px。
P1反馈window.alert 生硬 + 评论失败静默
  • 位置：删除/错误提示多处 alert()；评论提交失败无提示。
  • 问题：破坏视觉统一；失败无反馈用户不知道要重试。
  • 方案：引入轻量 toast 组件；评论失败状态明确展示。
P2移动端日历在移动端不可达
  • 位置：src/pages/calendar/index.astro 交互区。
  • 方案：窄屏切换纵向堆叠或横向滚动。

四、代码质量与可维护性（含安全）

P0安全Open-Redirect 可被反斜杠绕过
  • 位置：src/pages/api/auth/user/github.ts:14 与 src/pages/api/auth/user/github/callback.ts:32，校验为 next.startsWith('/') && !next.startsWith('//')。
  • 问题：该校验仅挡 //host，但浏览器会把 \host、/\host 规范化成外部地址——攻击者可构造 \evil.com 让已登录用户被重定向到钓鱼站。这是真实可利用的开放重定向。
  • 方案：校验同时拒绝 \（且不要只挡前缀），用 new URL(next, site) 解析后断言 origin 一致，或用安全跳转白名单；两处统一改。
P0安全AUTH_SECRET 为空时可派生密钥
  • 位置：src/lib/auth.ts:27 —— serverEnv('AUTH_SECRET') || sha256(ADMIN_PASSWORD)。
  • 问题：未配置 AUTH_SECRET 时由 ADMIN_PASSWORD 派生 HMAC 密钥。若 ADMIN_PASSWORD 弱或可枚举，攻击者可自行伪造管理员会话；这也让「能否伪造会话」依赖一个可变口令而非独立密钥。
  • 方案：生产强制要求 AUTH_SECRET，缺失直接拒绝启动（fail-fast），不要 fallback。
已排除误报草稿（status=draft）公开泄露 —— 经核实不成立
  • 核实结论：db/schema.sqlite.ts:32-64 的 articles 表根本不存在 status / draft 字段（仅有 type: tech|note|photo）。项目当前没有草稿机制，因此不存在该泄露面。
  • 处理：该项已从事实清单中移除，无需改动。若未来引入草稿功能，届时再补发布态过滤。
P1一致性点赞/评论计数非原子；HMAC 比较非常量时间
  • 位置：src/pages/api/likes/*（读改写计数）；src/lib/auth.ts:52,108 用普通 === 比 HMAC。
  • 问题：并发点赞可能丢失计数；=== 存在时序侧信道（低风险但可修）。
  • 方案：计数用数据库原子自增/唯一约束下计数；HMAC 用 timingSafeEqual。
P1健壮性saveDraft slug 冲突 / API 泄漏内部细节 / 测试缺口
  • 位置：src/pages/api/...（保存草稿 slug 无唯一性处理；错误响应直接回显 DB 报错）。
  • 问题：slug 撞车覆盖；错误信息暴露 schema/结构。
  • 方案：slug 冲突加后缀或报错；错误统一映射为通用信息；补 middleware.ts / db/index.ts 单测（当前零覆盖）。

六、整体重构优先级建议

P0 —— 立即处理（安全 + 首屏 + 核心可用性）

Open-Redirect 反斜杠绕过 AUTH_SECRET 缺失 fallback 伪造会话 草稿公开泄露 /moments 52 API 请求爆炸 移动端导航溢出 / 管理按钮不可达

P1 —— 本轮迭代完成（体验 + 可维护性）

超长页面拆分（study/settings/calendar/nav） 重复工具函数去重（dateKey/tags/热力图网格） 删除 migrate-photos-tags 遗留端点 ActivityHeatmap 全量查正文 照片 batchUpdateTags N+1 search 全量内存过滤 reduced-motion / 搜索框 focus / alert 替换 / 评论失败提示 点赞/评论计数原子化 + HMAC timingSafeEqual

P2 —— 持续优化（性能 + 整洁）

Bundle 体积（MarkdownEditor/simple-mind-map/gsap 异步分包） 缺索引 + dbWrite 串行并行化 设置 KV 重复收敛 / middleware 配置化 / dbWrite 单一实现 图片每次 sharp 转换缓存 补 middleware / db 单测
推进建议：先做 P0 四个安全/首屏项（风险最高、收益最大，且每项改动面小）；随后一个迭代专做 /moments 请求聚合 + 超长页面拆分；P2 可随功能迭代零碎消化。重构前后用 vitest 74 用例与 playwright 回归守住行为不回归。

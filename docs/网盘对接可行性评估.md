# 多厂商网盘对接：可行性评估与方案调研

> 评估日期：2026-09-13 ｜ 面向项目：My-Blog（Astro SSR @ Vercel）
> 结论先行：**功能可做，但「网站直连各厂商」这条路走不通；可行路径是引入一个自建统一适配层。**

---

## 一、可行性评估：先看三道硬约束

开发者直觉通常是「申请各厂商 API → 网站调它」。这条路在 2026 年已经被三道约束堵死，逐一验证如下。

### 约束 1：厂商开放政策（决定「能拿到的权限」）

| 厂商 | 个人开发者可得权限 | 关键限制 |
| --- | --- | --- |
| **百度网盘** | 实名认证后可建 1 个应用（企业 10 个） | ⚠️ **2026-06-03 后创建的应用，`download`/`listall`/`filemanager`/`precreate`/`meta`/`move` 等接口仅能访问 `/apps/{appname}` 目录**；应用用途选「个人使用」限 **10 个用户**，「公开发布」需上线审核 |
| **阿里云盘** | ❌ **无面向个人开发者的公开开放平台** | 现有第三方工具（aliyunpan 等）走的是**逆向客户端协议**，非官方授权，随时失效且有 ToS 风险 |
| **阿里云 PDS** | ✅ 有，但那是**企业级付费产品**（开通域、按量计费） | 不是「阿里云盘个人盘」的 API |
| **OneDrive** | ✅ Microsoft Graph API 完全开放 | 需 Azure AD 应用注册；国内访问速度不稳定 |
| **Google Drive** | ✅ 完全开放 | 国内浏览器访问受限（服务端调用不受影响） |
| **Dropbox** | ✅ 完全开放 | 国内访问受限 |
| **WebDAV 系**（坚果云/Nextcloud/群晖） | ✅ 标准协议，填地址+账号即可 | 覆盖率取决于你实际用哪家 |

**这一栏最重要的发现**：百度网盘的新应用被限制在沙箱目录内，意味着**「用户上传的文件转存到网盘任意位置」这个诉求，在百度新应用上拿不到权限**；阿里云盘则连正规入口都没有。凡承诺「支持全部主流网盘」的方案，要么是逆向破解，要么是走代理层。

### 约束 2：Vercel 函数体积上限（决定「文件怎么走」）

已核实 Vercel 官方文档：**函数请求体与响应体上限均为 4.5 MB（所有计划，含 Pro），超出返回 413 `FUNCTION_PAYLOAD_TOO_LARGE`**。这是基础设施层硬限制，没有开关可调。

对本站的直接影响：

- 上传一个大文件 → 经函数中转 → 网盘：**必崩**（4.5 MB 以上直接 413）
- 从网盘下载大文件 → 经函数流式回传：**同样受响应体 4.5 MB 限制**
- 官方给出的解法只有两条：**客户端直传存储**，或**用一个不跑在 Vercel 上的中转服务**

由此推出关键结论：**文件正文不能经过本站的 serverless 函数。**

### 约束 3：CORS（决定「浏览器能否直连厂商」）

网盘厂商的 API 面向服务端调用设计，**不返回浏览器可用的 CORS 头**，因此也不可能让浏览器带着 token 直接打厂商接口。这条直接把「纯前端直传厂商」的方案否掉了。

### 三约束叠加后的可行空间

```
文件要离开本站   → 不能走 Vercel 函数（4.5MB）
                 → 不能让浏览器直连厂商（CORS）
                 → 只能经由一个「独立于 Vercel 的中转服务」
```

于是问题从「对接 N 个厂商」转化为「**对接 1 个统一中转层，由它去对接 N 个厂商**」。这恰好也是你需求描述里的形态——「填写目标网盘的**登录地址**及**鉴权参数**」：一个地址 + 一组凭证，本身就是统一层的语义。

## 二、方案调研：四条路线与可复用组件

### 路线对比

| | A. 自建统一层（AList） | B. 逐厂商直连 | C. 纯 WebDAV | D. 离线下载拉取 |
| --- | --- | --- | --- | --- |
| 覆盖厂商 | **60+**（百度/阿里云盘/115/天翼/OneDrive/Google Drive/Dropbox/S3/WebDAV…） | 每家单独实现 | 仅支持 WebDAV 的（坚果云/Nextcloud/群晖） | 取决于中转层能力 |
| 网站侧要写的对接代码 | **1 套**（统一 API） | N 套 | 1 套（WebDAV 协议） | 1 套 |
| 大文件上传 | ✅ 传给它，它再传厂商 | ❌ 受 4.5MB 与 CORS 双重限制 | ✅ 但浏览器不能直连（仍要中转） | ✅ 不占本站带宽 |
| 厂商政策风险 | 由 AList 社区持续适配 | 自己扛 | 无 | 同 A |
| 部署依赖 | 需一台常驻设备（VPS/NAS/Docker） | 无额外设备 | 同 A | 同 A |
| 许可证 | AGPL-3.0 | — | — | — |

### 推荐方案：A + C（AList 统一层，同时暴露 WebDAV）

**[AList](https://github.com/AlistGo/alist)**（Go + Gin，48k+ star，AGPL-3.0）是当前最成熟的可复用组件，它已经把你需要的三件事都做好了：

**① 统一的文件操作 REST API**（网站只需对接这一套）

| 能力 | 端点 |
| --- | --- |
| 登录换 token | `POST /api/auth/login` |
| 列目录 | `POST /api/fs/list` |
| 获取下载直链 | `POST /api/fs/get` |
| **上传文件** | `PUT /api/fs/put`（或表单式 `POST /api/fs/form`） |
| 建目录 / 重命名 / 删除 | `/api/fs/mkdir`、`/api/fs/rename`、`/api/fs/remove` |

**② 下载投递策略已优化**：能直链就 **302 跳转到厂商 URL**（不经中转、不吃中转带宽），不能直链才走透明代理流式，且支持 **HTTP Range**（断点续传/视频拖进度）。

**③ 同一实例还同时暴露 WebDAV / S3 兼容 / FTP / SFTP 协议**——意味着「网盘管理页」的后续扩展不需要再写代码，换个协议接就行。

**④ 关键增值能力：跨存储复制 / 离线下载（Aria2、迅雷、PikPak）**——可以让文件**不经过你的浏览器和网站**，由 AList 直接从 URL 拉到网盘。这是绕开 4.5 MB 限制最优雅的一条路。

### 架构落地形态

```
浏览器 ──上传(≤4.5MB)──► 网站函数 ──► 网盘            [小文件直通]
   │                                                    
   └──分片/直传──► AList (自建, VPS/NAS/Docker) ──► 网盘   [大文件]
                        ▲
网站服务端 ──REST API────┘  (地址+token 存 settings)
浏览器 ──下载──► AList 直链 ──302──► 厂商 CDN          [下载不经中转]
```

网站侧只需实现一个 `alist-client` 薄封装：登录/持 token、列目录、上传（转发请求体）、取直链。**与具体厂商完全不耦合**——厂商协议变化由 AList 的驱动更新承担。

## 三、实现代价分析

### 开发成本（增量，基于本站现状）

| 模块 | 说明 | 相对量 |
| --- | --- | --- |
| 设置页配置项 | 「网盘对接」分区：服务地址 + 用户名/密码或 token + 测试连接按钮（沿用 SettingsForm 三处同步约定） | 小 |
| `lib/cloud-drive.ts` | AList REST 客户端封装（登录、token 缓存与刷新、错误归一） | 小 |
| 上传转存接口 | 网站函数接收文件 → 转发 AList；**≤4.5MB 走此路，超过则引导分片或离线下载** | 中 |
| 网盘管理页 | 文件列表（面包屑/分页）、上传（含进度）、下载（拿直链后跳转）、删除 | 中 |
| 错误与状态处理 | 厂商限流、token 失效、目录不存在、配额超限的友好提示 | 中 |

整体属于**中等规模功能**，与本站已有的「图床」模块（GitHub 图床 + R2 回落）结构高度相似，可复用其开关分流、失败回落、配置存 settings 的既有模式。

### 维护成本（真正的大头）

| 项 | 说明 | 风险 |
| --- | --- | --- |
| **中转层运维** | AList 需常驻运行（VPS/NAS/Docker），要管升级、证书、备份 | ⚠️ 中高：这是新增的一个「必须活着」的依赖 |
| 驱动失效 | 厂商改协议 → AList 驱动失效（阿里云盘反向工程驱动尤其脆弱） | ⚠️ 中：靠社区修，需跟随升级 |
| 凭证生命周期 | OAuth refresh_token 会过期、网盘改密码即失效 | 中：需要「重新授权」入口 |
| AGPL-3.0 | 自用/自托管不触发分发义务；但**若将来把服务对外提供，修改版源码有开源义务** | 低（当前场景） |
| 百度沙箱政策 | 新应用只能操作 `/apps/{appname}`，且个人版限 10 用户 | ⚠️ 中：能力天花板明确 |

### 主要限制（必须提前接受的）

1. **单文件 4.5 MB 天花板**：不经中转层的大文件上传无法走「网站→网盘」。可行替代：前端分片多次请求、或直接引导用户用 AList 自带的 WebDAV/网页界面、或让 AList 离线下载从 URL 拉取。
2. **百度网盘能力受限**：2026-06 后的新应用受沙箱目录限制；想全盘读写需企业认证或走 AList 的既有驱动（其 token 机制与之不同）。
3. **阿里云盘无官方 API**：只能依赖 AList 的反向工程驱动，属于「能用但无保障」。
4. **国内网络**：Google Drive/Dropbox 在浏览器侧体验差；服务端（Vercel 美国节点）调用正常。
5. **新增基础设施**：中转层意味着多一台要维护的设备/容器，以及一条必须保证可用的链路——这是**为能力付出的架构税**。

## 四、落地建议（分阶段）

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **P0** | 设置页加「网盘对接」分区（地址 + 鉴权 + 测试连接），`lib/cloud-drive.ts` 打通 AList 登录/列目录 | 一台可跑的 AList（本机 Docker 即可起步） |
| **P1** | 网盘管理页：目录浏览 + 下载（直链 302）+ 小文件上传（≤4.5MB 经函数） | P0 |
| **P2** | 大文件方案：前端分片上传，或接入 AList 离线下载（从本站文件 URL 直接拉取，不占带宽） | P1 |
| **P3** | 与本站图床打通：上传的图片/附件可选「存 R2」或「转存网盘」，统一资产视图 | P2 |

**推荐起步动作**：先在本机 `docker run -d -p 5244:5244 xhofe/alist:latest` 起一个 AList，配一个网盘（WebDAV 系最稳，如坚果云），用它的 Web 界面 + API 验证「列目录 / 上传 / 取直链」三件事。**这一步能在一小时内证明整条链路是否成立**，成本极低，值得先做再决定是否投入 P1 以上的开发。

---

## 五、一句话结论

> **能做，但正确的实现不是「网站对接 N 个厂商」，而是「网站对接一个自建统一层（AList/WebDAV），由统一层去对接厂商」。**
> 核心不可绕过的限制是 **Vercel 4.5 MB 体积上限** 与 **厂商（尤其百度 2026 新政、阿里云盘）的政策收紧**；
> 前者决定了「必须有一个不在 Vercel 上的中转」，后者决定了「不要自己逐个对接」。
> 主要代价不在写代码，而在**多出一台要长期维护的中转服务**。

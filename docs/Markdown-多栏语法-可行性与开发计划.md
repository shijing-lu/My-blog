# Markdown 两栏／三栏：可行性与开发计划

日期：2026-09-27  
阶段：首版已实现（2026-09-28）；下文保留开发前的调研与估算，实际用法见 [多栏使用与实现说明](Markdown-多栏使用与实现说明.md)。

## 实施记录

- 冻结 `:::columns` + `::column` 语法，无须新增依赖或修改数据库结构。
- 完成共享扫描器、remark AST 转换、阅读组件与容器宽度响应式布局。
- 共用 MarkdownEditor 的轻量模式与 WYSIWYG 模式均提供两栏／三栏按钮和栏内 CodeMirror 编辑。
- 完成选区转换、添加第三栏、左右移动、合并移除、展开普通正文、源码切换、保存与父编辑器撤销链路。
- 表格结构操作前显式提交尚未失焦的单元格内容；临时未闭合代码块／指令通过编辑事务中的已知边界保持当前栏。
- 首版范围仍为等宽两栏／三栏；列宽拖拽、嵌套多栏与跨行合并不在本次范围。
- 性能实现：按不可变文档缓存分栏扫描结果，复用已有栏编辑器，单栏修改回写其源码范围；每次文档修改仍有一次结构扫描，并非全文增量解析。键入不触发整篇 MDX 编译。
- 先前开发验证：渲染相关 146 项通过；分栏、表格和编辑器性能相关 21 项通过（含重叠用例）。浏览器流程覆盖输入、换行、撤销重做、模拟中文组合输入、保存、移动合并、工具栏目标、表格内容提交及窄屏布局。10 万字符量级样本连续输入 20 键约 348ms，含自动化开销，不能视为单键延迟或真实设备性能保证。后续未闭合输入边界修正不在这一轮浏览器结果内。

## 1. 结论

**可行，整体难度中高。** 阅读页的多栏排版可以沿用项目现有的 MDX 指令、React 组件和 CSS Grid；真正困难的是让每栏保留完整的块级 Markdown，同时在 CodeMirror 中像表格一样直接编辑，并保证撤销、自动保存、粘贴、焦点和长文性能可靠。建议先交付两栏／三栏的语法与阅读渲染，再完成可视化编辑。初版限定一组多栏只有一行，列内可以有任意多个 Markdown 块；窄屏折叠为单列。

**不要把 GFM 表格当多栏容器。** 表格单元格主要适合行内内容，难以自然容纳多段落、列表、围栏代码与块级公式。项目已有 `:::grid` 是图片画廊专用，应保留原语义，新建独立的 `:::columns` 语法。

## 2. 用户体验与范围

1. 工具栏提供“二栏”“三栏”入口，插入后直接聚焦第一栏；将已有选区转换时，选中文本默认放入第一栏，其余栏为空。
2. 编辑态显示真正的并排栏。点进任一栏可以直接输入、选择、粘贴 Markdown 内容；常见加粗、列表、图片、公式等命令在当前栏生效，作者无需接触多栏定界符。
3. 每栏可写段落、标题、列表、引用、链接、图片、表格、代码块和公式；内容存成可读的 Markdown 源码。阅读页桌面端并排，容器宽度不足时顺序堆叠。
4. 提供“增／删栏”“二栏⇄三栏”“左／右移动”操作。删除非空栏必须保留内容，可先合并到相邻栏或提示选择目标，绝不静默丢弃。
5. 编辑器可一键“显示源码”处理高级场景。错误或不完整语法应回退为可编辑源码，不得让页面白屏或丢失文字。
6. 初版最多三栏，不提供列宽拖拽、跨行合并或嵌套多栏。多栏可以放在普通文章和文档文章；随心录等共用渲染器的地方应能安全显示，工具栏入口按实际编辑容器决定。

## 3. 当前项目的技术事实

| 环节 | 当前实现 | 对本功能的影响 |
| --- | --- | --- |
| 内容存储 | 数据库存 Markdown／MDX 原文；文章、文档等经 `renderMdx()` 阅读渲染 | 以 Markdown 为唯一事实源，无须改数据库模式 |
| 语法 | `src/lib/mdx.ts` 预处理源码，`src/lib/mdx-plugins.ts` 使用 `remark-directive` 转换指令；已有 `:::grid`、折叠、选项卡 | 可以扩展一个受控容器指令，但必须避开现有 `grid` 名称及指令嵌套陷阱 |
| 组件 | `src/components/mdx/registry.tsx` 注册 React MDX 组件；`Grid.tsx` 只排图片 | 新建语义清楚的 `Columns`／`Column` 组件与样式，不复用图片网格规则 |
| 编辑器 | `MarkdownEditor.tsx` 是共用 CodeMirror 6 编辑器；文档 `DocInlineEditor.tsx` 与写作台复用它 | 一处实现工具栏与可视化编辑，可覆盖主要编辑入口 |
| 表格编辑 | `cm-table.ts` 用 `WidgetType` + `contenteditable` + transaction 回写 Markdown；`cm-wysiwyg.ts` 用 `StateField` 提供跨行 `Decoration.replace` | 可借鉴 Widget、事务、焦点恢复，但多栏需要块级内容，不能只复制表格的纯文本单元格方案 |
| 性能 | WYSIWYG 按需加载，装饰有缓存；长数学文档渲染曾达到数秒以上 | 多栏 Widget 应按块增量更新，避免每次按键重新编译整篇 MDX |
| 样式 | 阅读内容为 `.prose`；已有图片 `.md-grid` CSS | 多栏需独立排版并覆盖 typography 对子元素的默认外边距 |

## 4. 候选语法与取舍

### 推荐草案：一个容器，独立列标记

````markdown
:::columns
::column
### 左栏

这里是 **Markdown**，也可以有列表：

- 第一项
- 第二项

::column
### 右栏

![插图](/api/images/example)

```ts
console.log('代码块也在本栏');
```
:::
````

三栏只需写三个 `::column`。列数由标记数决定，必须恰好为 2 或 3。`::column` 需独占一行；容器首尾保留空行以减少 Markdown 解析歧义。与现有指令嵌套时遵守项目约定：外层围栏比内层多一个冒号。工具栏负责生成标准写法，用户通常无需手写。

**此语法尚是待验证草案。** 第一开发步骤要用当前锁定版本的 `remark-directive` 和 MDX 管线确认：`::column` 在容器内被解析成独立叶节点，列中的围栏代码、嵌套指令、表格与数学公式均保持原语义。若解析不稳定，再改为显式行分隔标记并写专用 micromark／remark 解析扩展；不能靠简单正则按 `::column` 切正文，否则代码块中的同名文本会被误切。

| 方案 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- |
| GFM 表格 | 编辑器已有可视化表格 | 单元格不适合完整块级 Markdown | 不采用 |
| 复用 `:::grid` | 少一个组件 | 改变图片画廊含义，影响灯箱与旧文档 | 不采用 |
| 直接写 `<Columns><Column>` MDX | 渲染实现简单 | 手写成本高，错误 JSX 可能使整篇编译失败；普通 Markdown 可移植性差 | 仅作内部结构参考 |
| `:::columns` + `::column` | 人可读，贴近现有指令架构；每栏有清楚边界 | 需验证指令解析及嵌套行为 | 推荐，先做解析探针 |

导出原文时保留自定义语法；其他 Markdown 阅读器未必认识它。若将来需要通用导出，可另加“多栏转顺序章节／HTML”的导出选项。

## 5. 技术设计

### 5.1 服务端渲染

- 在 `remark-directive` 之后处理 `columns` 容器：仅接纳 2／3 个直接子级 `column` 标记，按标记切分 mdast 子节点，构造 `<Columns>`、`<Column>` MDX JSX 节点；各栏原有 Markdown AST 子树直接迁入，不对正文做字符串重新解析。
- 对非法列数、未闭合容器、混入标记前的内容制定确定规则：优先保留原文并提示作者；不得吞掉内容。解析器只认白名单语法与列数，不开放任意样式或可执行属性。
- `Columns` 输出语义清楚的静态 DOM，CSS Grid 使用 `minmax(0,1fr)`。按**内容容器宽度**决定两／三列或单列，避免在桌面端窄文档栏里产生横向滚动；没有 JS 布局循环。
- 明确目录与锚点行为：栏内标题按 DOM 顺序进入目录，点击目录后仍能正确滚动定位；图片灯箱继续按现有规则工作。
- `renderMdx` 的全部调用方统一获得能力，重点检查 `/blog/*`、`/doc/*`、文档预览 API、动态／日记和导出原文。独立的轻量 `renderMarkdownHtml` 管线不自动支持该语法，需决定其调用场景是否要显示多栏。

### 5.2 可视化编辑

- 新建多栏块的结构解析器：找出完整块的源码范围、每栏内容范围和对应偏移。扫描需识别围栏代码、转义、外层容器与缺失闭合；不以笼统全局正则匹配。
- 在 `cm-wysiwyg.ts` 中将完整块替换为 `ColumnsWidget`。**跨行 `Decoration.replace` 必须由 `StateField` 直接提供**；与表格、代码块、公式等已有装饰范围不得重叠。失败时显示原源码。
- Widget 内每栏采用独立的可编辑区域，映射到主 CodeMirror 文档的对应源码片段。优先评估“每栏一个轻量 CodeMirror 子编辑器”，让多段落、列表、快捷键、IME、撤销更自然；避免以整栏 `contenteditable` + `textContent` 回写，因为那会抹掉 Markdown 结构。
- 子编辑器修改经单次主文档 transaction 写回对应栏；保存仍走现有 `MarkdownEditor` 的 `onChange`／自动保存链路。设计明确焦点恢复、光标偏移、粘贴、多行删除、撤销重做和编辑器销毁时的 flush。结构命令作为一次可撤销事务处理。
- 不在每次键入时调用服务端 `renderMdx` 或在多个子编辑器里重复加载完整 WYSIWYG。先实现当前栏即时 Markdown 视觉反馈，再视性能决定是否渲染复杂公式和嵌套块；离开栏时可显示更完整的预览。
- 写作台的轻量 `livePreview` 首期可以保留源码编辑和快捷插入，但必须能安全显示语法；完整“像表格编辑”能力在 WYSIWYG 模式提供。是否把同样的可视编辑扩到轻量模式，由后续使用场景决定。

### 5.3 易用性与无障碍

- 工具栏入口清楚标注“二栏”“三栏”，而非只放图标；插入后用 Tab／Shift+Tab 在栏间移动，箭头键仍在栏内移动。
- 每栏有可感知的序号／标签，读屏器能获知“第 1 栏，共 2 栏”；在窄窗口竖排时保持阅读顺序。
- 栏操作菜单和源码切换均可键盘触达；错误提示指出哪一栏或哪一行有问题，不直接丢失编辑内容。

## 6. 开发阶段与交付门槛

| 阶段 | 工作 | 完成标准 | 粗估 |
| --- | --- | --- | --- |
| A 语法探针与规格冻结 | 用当前依赖验证推荐语法、围栏代码、嵌套指令、空栏及坏语法；冻结规范 | 正文不被误切，坏语法不丢字、不使整篇白屏 | 0.5～1 天 |
| B 阅读渲染 | remark 转换、组件注册、CSS Grid／容器查询、目录和灯箱检查 | 博客／文档／预览一致，窄容器不横向滚动 | 1～2 天 |
| C 快捷插入与结构操作 | 工具栏入口、选区转换、二三栏切换、删栏保文 | 无需手写定界符即可插入和改结构，操作可撤销 | 1～2 天 |
| D 可视化栏编辑 | 块解析、Widget、栏内编辑、主文档事务和焦点同步 | 不碰源码即可改两／三栏内容；列表、代码、图片、公式可编辑 | 3～5 天 |
| E 兼容与交付 | 长文性能、IME、撤销、保存、移动端、语法手册、桌面便携版覆盖 | 编辑／阅读无白屏、无数据丢失；覆盖既有 `release/portable` 目录 | 1～2 天 |

**合计约 6.5～12 人日**，其中 D 的范围决定最大不确定性。估算基于当前代码阅读，尚未实现或压测；A 阶段若发现指令解析需要自定义 micromark 扩展，需重新估算。建议 B 完成后先让用户确认实际阅读排版，再进入 D 的交互细节。

## 7. 必须覆盖的边界

- 空栏、只有一段、多个段落、列表和嵌套列表、引用、标题、代码块中出现字面 `::column`、栏内已有 `:::` 指令、表格、图片、链接、行内及块级公式、中文输入法组合态。
- 插入、删除、移动一栏；二栏转三栏与三栏转二栏；删除非空栏保留内容；撤销与重做连续编辑；自动保存时切换文章／关闭编辑器。
- 缺闭合、重复标记、超出三栏、只有一栏、分隔标记出现在围栏代码内。出错时继续展示和编辑源码。
- 320px 手机、桌面窄文章栏、放大字体、暗色主题；没有水平滚动，列内长代码可在该列局部滚动。
- 长文只对变化的多栏块重新解析／更新。记录输入延迟和装饰构建耗时，不能把既有长文问题放大。

## 8. 模型选择与额度控制

按 [OpenAI 官方模型选择指南](https://developers.openai.com/api/docs/guides/model-selection) 和 [Codex 代码生成指南](https://developers.openai.com/api/docs/guides/code-generation)：

| 任务 | 建议模型／推理强度 | 原因 |
| --- | --- | --- |
| A 的解析设计、D 的状态同步方案、疑难白屏或数据丢失审查 | GPT-6 Astra，medium／high | 跨 MDX、CodeMirror、React、保存链路；错误代价高 |
| B／C 的明确实现和多数 D 子任务 | **GPT-6 Sol，medium（默认推荐）** | 官方定位为日常编码与研究的平衡选择；本项目已有清晰扩展点 |
| 文档整理、单文件样式与入口文案等边界清楚的小任务 | GPT-6 Luna，low／medium | 适合范围明确的修改，成本和延迟较低 |

额度策略：先用 Sol 完成语法探针和可分解实现；只把未解决的跨层问题升级给 Astra；小范围重复劳动才用 Luna。每个任务只提供相关文件与复现样例，阶段完成后再继续下一阶段，避免反复把整个项目喂给模型。模型在 Codex 中的可用性与账号额度以用户界面实际显示为准；[API 价格页](https://developers.openai.com/api/docs/pricing) 只能说明 API 单价，**不能换算成 Codex 订阅额度消耗**。正式开发前可用同一个解析样例比较 Sol medium 与 Astra medium 的正确率、修复回合数和实际额度，再固定组合。
